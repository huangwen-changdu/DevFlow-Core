# DevFlow Runtime References

- Trigger: DevFlow-Core structure, skill framework layout, docs vs references, runtime method source, generated plan docs, Codex onboarding, install file map, target runtime files, user-level runtime files, project-knowledge skill, published skill manifest, script execution model, hooks, global config vs project runtime, project-only AGENTS and CLAUDE.
- Lesson: Runtime framework methods should live beside the skills that use them, not under `docs/`; every newly reachable runtime skill must be present in plugin metadata, target and user installer manifests, and installer regression checks or the installed handoff can break despite source-package rules being correct. Lifecycle owner boundaries must remain explicit: Brainstorm confirms requests then the user selects A/B/C; only named deterministic success edges flow directly (A Spec -> Cut -> Plan -> Build -> Prove, B Cut -> Plan -> Build -> Prove, C Cut -> Build -> Prove). Missing or changed depth, Cut non-PASS, scope drift, Build blocks, Proof FAIL/BLOCKED, changed intent, and PUA recovery return facts to Core for selection. When changing lifecycle order, update runtime surfaces, diagrams, self-tests, and validators; assert both direct-success and Core-return contracts rather than only prose presence. Keep static Plan Pack structure checks separate from lifecycle-state checks. Static plan validators must reject semantic placeholders, not merely require labels: validate recognizable symbol/anchor locations, substantive mechanics rather than a `pseudocode` token, and an implementation mechanism on each code-edit step; add one isolated negative self-test per bypass. Onboarding docs must show which rules, skills, commands, references, and runtime scripts are installed into the target project, which skills/commands/scripts can install to the user level, whether scripts run automatically or require agent/user/command triggering, how personal Codex defaults differ from project-versioned runtime files, and that `AGENTS.md` plus `CLAUDE.md` are project-level files only.
- Next action: Next time adding or changing a DevFlow runtime skill or cross-skill handoff, first classify each transition as a deterministic direct successor or a non-unique Core-return exception; then check `plugin.json`, `gemini-extension.json`, `scripts/install-devflow.js`, `scripts/install-devflow-user.js`, and both installer validators. Run package, trigger, host, plan, and user-runtime checks. Do not validate source rules alone, route every artifact through Core, or couple static plan validation to lifecycle state.
