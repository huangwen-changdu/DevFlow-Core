# 失败卡: 建议/设计类产物漏写实现边界与能力局限声明

> 摘要: 用途=防止建议/设计类产物漏写实现边界与能力局限声明 | 做了什么=记录触发/根因/修复/防复发，已召回 2 次 | 复用入口=产出任何方案/设计/报告类文档前，对抗轮必查两问（边界写明了吗、局限诚实声明了吗） | 更新时间=2026-08-23

- 触发: 循环产出「优化建议报告」，停止条件初检通过（标题数、优先级标签、最小改动路径齐备），但收尾对抗轮发现 2 个真问题：① 建议的校验器方案未写明解析边界（会撞上状态文件历史段误报）；② 未声明「文件级校验只能验证声称、不能验证行为」的局限。
- 根因: 写建议时把实现细节当隐含知识（校验器只解析当前循环段），把能力边界当默认共识（退出码真伪无法由文件校验证明）；建议类产出物的结构检查（标题/标签/路径）天然覆盖不到这两类缺陷。
- 修复: 在建议条目内补「实现边界」句（解析范围/作用域/排除项），在总览补「局限声明（诚实边界）」段（能验证什么、不能验证什么、缓解手段是什么）。
- 防复发: 产出任何「建议/设计/方案」类报告时，对抗轮除常规四查外必查两条——① 每条建议是否写明实现边界（作用域、解析范围、排除项）；② 方案能力局限是否诚实声明并附缓解手段。

召回记录:
- 2026-08-23 harness-improvement-proposal: 本卡由该循环收尾对抗轮生成（发现并已修复）。
- 2026-08-23 loop-docs-sedimentation: 采纳——设计摘要头/INDEX 索引格式时必写实现边界（索引是静态快照，需维护机制；摘要头靠 grep 机检而非语义理解）与局限声明（文件级校验验证不了行为真实性）。
