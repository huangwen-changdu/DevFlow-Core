# Loop 工程 × Harness 引擎五概念：优化与进步点分析报告

> 摘要: 用途=基于视频 Harness 五概念给出 Loop 工程优化与进步点建议 | 做了什么=现状对照 + 差距分析 + 12 条带优先级（P0/P1/P2）建议 + 分阶段落地清单 | 复用入口=要实施 Loop 工程优化（校验器、阶段显式化、委托审查）时先读落地清单 | 更新时间=2026-08-23

> 输入：视频学习总结（Harness 引擎：阶段 / 阶段状态机 / 门控 / 执行者 / 子智能体，核心主张「引擎管流程，模型执行」）。
> 调查对象：`dsh/plugins/dsh-loop-engine` 插件 + `dsh/agent-presets/loop-engine` 权威源 + `loop/` 工作目录。
> 结论口径：**现状对照 → 差距 → 建议（P0/P1/P2 + 最小改动路径）→ 分阶段落地清单**。全部建议为 prompt/资产/零依赖脚本改动，不建宿主级引擎（尊重 spec 已拒绝的选项 3）。

## 总览与结论

Loop 工程现状一句话：**有流程，无引擎**。

| 视频指出的缺口 | Loop 工程现状 | 判定 |
|---|---|---|
| 无质量门控（AI 觉得完成就停） | 有确认门、检查点、空转 blocked、对抗轮、反规避表——但**全是 prompt 约定**，模型可以声称「过了对抗轮」而不做，无人/无脚本能查证 | 有约定，无强制 |
| 无流程一致性（模型可跳过步骤） | 每轮五步纪律、状态文件格式都写死在 SKILL.md，但下一步「自己琢磨」——转移完全由模型自决，无确定性状态机 | 有流程，无确定性 |
| 无附着性（方法无法沉淀分享） | **已解决，是本工程最大亮点**：skill / 4 模板 / loop-state.md / loop/learned/ 失败卡全落盘可召回，方法可跨会话复用 | ✅ 亮点 |

**核心结论**：视频主张的「引擎管流程，模型执行」在 Loop 工程里正好缺了「引擎」这一半。仓库内已有可复制的范式——DevFlow 用 `npm run verify:all`（16 项零依赖校验器）硬性驱动流程一致性（见 `docs/2026-07-31-harness-flow-review.md`），Loop 工程目前只有 1 个测试（`test/sync.test.js`，只测资产同步），协议层零校验。

**推荐的总方向**（两档，均不违反 spec 2026-08-21 的既有取舍）：
1. **确定性验证层**（仿 DevFlow 零依赖校验器）——把「门控证据」变成脚本可机检的客观事实；
2. **协议显式化**——把隐式的阶段/门控/执行者概念在 SKILL.md 里命名成显式结构，并补上委托执行与独立审查的用法指引。

---

**局限声明（诚实边界）**：文件级校验器只能验证「声称」的一致性（对抗轮结论存在、状态枚举合法、编号连续），**无法验证「行为」的真实性**（模型可能编造退出码）。缓解手段：停止条件一律写成可重放命令（人/CI 可随时重跑同一命令复核），校验器管「记录一致」，重放管「行为真伪」——两者叠加才接近视频的「硬驱动」。

## 一、阶段（Stage）

**现状对照**
- 视频的 Stage 四要素（工作手册 + 工具箱 + 门控 + 下一站）在 Loop 工程里是**隐式存在**的：工作手册 = SKILL 规则段与 4 个模板（`templates/fix-bug-to-green.md`、`implement-feature-to-green.md`、`generic-task.md`、`from-plan.md`）；工具箱 = preset 挂载的完整工具面；门控 = 确认门/检查点；下一站 = 「每轮五步」里的自检转移。
- 但没有「阶段」这个命名层：状态文件没有「当前阶段」字段，阶段边界靠模型临场把握。模板是工作手册的好雏形，但缺**审查类、规划类**阶段模板（现有模板都是编码/通用执行向）。

**建议**
- **P1**：SKILL.md 增加「阶段」命名节——把现状隐式阶段显式化为五个命名阶段：`起草（draft）→ 确认（confirmed，人工门）→ 执行轮（running）→ 收尾对抗（adversarial，条件门）→ 完结（done）`，每阶段按视频四要素写一行（工作手册指向哪个模板/规则段、工具箱限哪些工具、门控是什么、下一站是谁）。**最小改动路径**：`assets/skills/loop-engineering/SKILL.md` 新增一节（约 20 行）+ 状态文件格式增加「当前阶段」行 + 两个模板的字段块同步。
- **P2**：新增「审查/规划」类阶段模板（如 `review-stage.md`：阶段门控 = 人工放行，工具箱 = read/grep/ask_user，产物 = 审查结论入状态文件），让非编码任务（如本次分析报告循环）有对应工作手册。**最小改动路径**：`templates/` 下加 1–2 个模板文件，SKILL 模板节列名。

## 二、阶段状态机（Stage State Machine）

**现状对照**
- 视频的「调度中心确定性决定下一步」在 Loop 工程里**完全没有宿主实现**：`lib/index.js` 只做资产同步与系统公告；下一步转移由 SKILL 的「决定下一步：自己琢磨该干什么」交给模型自决。
- spec 2026-08-21 已明确拒绝「自定义循环工具插件 / 宿主级引擎」（选项 3），所以**不能**用 cordis 服务实现真状态机——但可以用仓库既有的**零依赖校验器范式**（`scripts/validate-learning-loop.js`）做确定性兜底：脚本不决定下一步，只**硬性校验**模型声称的转移是否真实发生（这正是「引擎管流程」的最小形态）。

**建议**
- **P0**：状态枚举化——`loop-state.md` 的「当前状态」从自由文本改为固定枚举（`draft / confirmed / running / blocked / done`），合法转移表写进 SKILL（如 `done` 必须来自对抗轮通过、`blocked` 必须连续 2 轮无推进）。**最小改动路径**：SKILL 状态文件格式段 + 现有模板字段块（4 处小改）。
- **P0**：新增零依赖校验器 `scripts/validate-loop-state.js`（仿 `validate-learning-loop.js`）：断言六要素齐备、轮次编号连续（R1…Rn）、当前状态枚举合法、`done` 时对抗轮结论必须存在、失败卡文件存在；挂到 `package.json` 加 `loop:verify` 脚本。**实现边界**：校验器只解析「当前循环」段（自 `## 循环定义` 至 `## 历史` 分隔线为止），历史段/旧循环编号一律忽略，避免对归档内容误报。**最小改动路径**：新建 1 个脚本（约 80 行，node:fs/node:path）+ package.json 一行。
- **P2**：状态转移图文档（`docs/loop-stage-diagram.md`，ASCII 图 + 转移条件表），把五阶段转移画成确定图供人审阅，也是校验器的规范来源。**最小改动路径**：新建 1 个文档。

## 三、门控（Gating）

**现状对照**
- Loop 工程已有门控萌芽且方向与视频三模式高度吻合：**人工放行** = 循环定义确认门、检查点（每 N 轮暂停）；**自动放行** = 每轮自检命令退出码；**条件放行** = 对抗轮通过门、空转 blocked 判定。
- 差距：三模式没有被命名成体系；所有门控**只有约定没有证据**——模型可以声称过了对抗轮而不做（反规避表有「跳过对抗轮」条目，但拦截方式仍是 prompt，不是校验）。

**建议**
- **P0**：把对抗轮结论从「要求写入状态文件」升级为「校验器可机检」——`validate-loop-state.js` 在 `done` 状态下强制检查对抗轮段存在且含「最可能错的地方」字段，缺则判定循环未真正收尾（对应 P0 校验器同一脚本，零额外改动）。
- **P1**：SKILL 门控节显式三模式命名——`人工门（确认门/检查点，ask_user 强制）`、`自动门（每轮停止条件命令）`、`条件门（对抗轮/空转，判据客观可查）`，每个门控写明「放行证据必须落到状态文件哪一行」；反规避表加一条「门控声称但无证据落盘 → 校验器红灯」。**最小改动路径**：SKILL.md 门控节（约 15 行）+ 反规避表一行。
- **P2**：条件门判据库——把常用客观判据（`node <test>.js` 退出码 0、`grep -c` 计数、`test -f` 文件存在、hash 比对）做成 `templates/` 下的判据片段，起草停止条件时直接选用，减少自由发挥导致不可验证。**最小改动路径**：新增 1 个模板文件。

## 四、执行者（Runner）

**现状对照**
- 视频的两种模式中，Loop 工程**只有「本机执行」**被协议覆盖：SKILL 全程默认主循环自己干活（每轮五步）。「委托执行」在平台层可用（`tool-subagent`、`tool-workflow`、`tool-ralph` 都挂在 preset 里），但 SKILL 从未指引「什么阶段该委托给独立专家」——对抗轮就是「自己换批评者角色审自己」，这正是视频指出的客观性盲区。

**建议**
- **P1**：SKILL 增加「执行者」节——明确两种模式与选择规则：本机执行 = 默认（执行轮、小任务）；委托执行 = 收尾对抗轮与大任务审查阶段，可把「独立审查」委托给子智能体（见下节），委托结果只作证据、判定权仍在本机。**最小改动路径**：SKILL.md 一节（约 12 行）+ 收尾报告清单加「审查者类型（本机对抗 / 委托审查）」一行。
- **P2**：委托模板（可选扩展）——`workflow` 多审查角度扇出脚本模板（对应「审查、测试等需要判断是否通过」的条件门场景），仅作可选路径，不入默认循环路径，避免加重常规任务负担。**最小改动路径**：`templates/` 下加 1 个模板 + SKILL 模板节一行。

---

## 五、子智能体（Sub-Agent）

**现状对照**
- 平台层齐备：`agent.cordis.yml` 的 delegation 组挂载了 `subagent`（spawn）、`subagent_fork`（fork，继承上下文）、`workflow`、`ralph`（maxRounds 64）；`codex` / `claude-code` 两个产品 provider 行存在但默认 `disabled: true`。
- 差距：SKILL 没有任何「独立工作区 + 专属模型保证审查客观性」的用法——协议里的对抗轮是**自我换角色**，与视频「外包给独立专家确保客观」的核心手段正好相反。独立上下文（spawn）与继承上下文（fork）的选择规则完全缺失。

**建议**
- **P1**：SKILL 对抗轮节升级——写清审查者选择规则：小任务收尾用本机对抗（换批评者角色，成本最低）；中大任务或「结论影响面大」时，用 `subagent`（spawn，独立上下文）做**干净上下文审查**（不继承本会话上下文，避免「我审我自己」的盲区），审查结论写入状态文件作为对抗轮证据；`subagent_fork` 留给继承上下文的跟进分析。**最小改动路径**：SKILL 对抗轮节（约 8 行改动）。
- **P2**：README 补充「可选审查模型」说明——如何启用 `codex` / `claude-code` 行（复制 preset 去掉 `disabled`，与 agent.cordis.yml L299-301 注释一致），作为需要专属模型审查时的配置入口。**最小改动路径**：README 加一段。

## 分阶段落地清单

| 阶段 | 改动 | 优先级 | 最小改动路径 |
|---|---|---|---|
| Phase 1（确定性验证层，先做） | 状态枚举化（draft/confirmed/running/blocked/done）+ 合法转移表 | P0 | SKILL 状态文件格式段 + 4 模板字段块 |
| Phase 1 | `scripts/validate-loop-state.js`（六要素/轮次连续/枚举合法/done 必带对抗轮结论）+ `npm run loop:verify` | P0 | 新建 1 脚本 + package.json 1 行 |
| Phase 2（协议显式化） | SKILL 新增「阶段」节（五阶段 × 四要素） | P1 | SKILL.md + 状态文件「当前阶段」行 |
| Phase 2 | SKILL 门控节三模式命名 + 放行证据落盘要求 + 反规避表加「门控无证据」条目 | P1 | SKILL.md 门控节 |
| Phase 2 | SKILL「执行者」节（本机/委托选择规则）+ 收尾报告加「审查者类型」行 | P1 | SKILL.md 一节 |
| Phase 2 | SKILL 对抗轮委托规则（spawn 干净上下文 vs fork 继承上下文） | P1 | SKILL 对抗轮节 |
| Phase 3（体验与扩展） | 审查/规划类阶段模板 + 判据库模板 + 委托（workflow 扇出）模板 | P2 | templates/ 加 2–3 文件 |
| Phase 3 | 状态转移图 `docs/loop-stage-diagram.md` | P2 | 新建 1 文档 |
| Phase 3 | README 补可选审查模型（codex/claude-code 行启用方式） | P2 | README 一段 |

**不做的事**（边界声明）：不建宿主级 cordis 服务/状态机（spec 选项 3 已拒）；不新增依赖（沿用 node:fs/node:path 零依赖范式）；不改 dsh-devflow；不动「两阶段锚定」bootstrap（与本次优化无关）。
